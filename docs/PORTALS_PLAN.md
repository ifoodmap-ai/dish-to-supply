# iFoodmap 三端後台架構擴增規劃

> 目標:從「AI 分析 + 人工媒合」升級成**餐廳端 / 供應商端 / 平台端三個完整後台**,
> 並把 AI 能力分配到各端,讓每一次交易都在餵養平台的資料資產。
>
> 撰寫日期:2026-07-26 · 對應目標:三個月內完成種子輪

---

## 0. 現況盤點

| 端 | 現有入口 | 頁數 | 問題 |
|---|---|---|---|
| 餐廳(買家) | `/my` | 1 | **沒有後台**。只能看詢價歷史,看不到出貨、無法確認收貨、沒有成本工具 |
| 供應商 | `/supplier/*` | 5 | 只有「接單→出貨」的被動流程,沒有任何主動賺錢的工具 |
| 平台管理員 | `/admin/*` | 9 | 交易流程完整,但**沒有會員管理、沒有資料主檔維護** |

**三個結構性缺口:**

1. **收貨鏈斷裂** — 供應商說出貨了就沒有下文,平台不知道貨到沒到 → GMV / 複購率算不出可信數字
2. **沒有食材主檔** — 供應商講「一箱/一簍/一台斤」,同一個東西十種寫法,媒合只能做字串比對 → **真正的比價不可能成立**
3. **餐廳端沒有留下來的理由** — 用完一次 AI 分析就走了,沒有任何日常會回來用的工具

## 1. 餐廳後台 `/restaurant/*`(全新)

### 角色設計

新增 `role = 'restaurant'`,並支援**一店多人、一戶多店**(連鎖店必要):

| 角色 | 權限 |
|---|---|
| `owner` 老闆 | 全部,含成本毛利、成員管理、跨分店彙總 |
| `manager` 店長 | 該分店的採購、收貨、簽核;看得到成本 |
| `purchaser` 採購員 | 只能建立採購需求,送出需店長簽核;**看不到成本毛利** |

### 導覽結構

| # | 頁面 | 路由 | 內容 | AI 功能 |
|---|---|---|---|---|
| 1 | **營運總覽** | `/restaurant` | 本月採購金額(與上月比)、待收貨、待評價、食材成本佔營收比、本月省下多少(vs 同區均價) | — |
| 2 | **我的菜單** | `/restaurant/menu` | 上傳的菜單、辨識出的菜色、每道菜的食材組成與**單份成本、毛利率** | ⭐ **菜單成本毛利分析** |
| 3 | **智慧採購** | `/restaurant/purchase` | AI 產生的建議採購清單、一鍵成單、LINE 叫貨綁定 | ⭐ **自動補貨提醒**<br>⭐ **LINE 語音/文字叫貨** |
| 4 | **訂單與收貨** | `/restaurant/orders` | 訂單列表 + 出貨進度 + **「已收到貨」按鈕** + 拍送貨單自動核對 | ⭐ **送貨單拍照對帳** |
| 5 | **成本與省錢** | `/restaurant/costs` | 食材價格趨勢、漲價預警、替代建議、囤貨時機 | ⭐ **漲價預警 + 替代食材**<br>**採購時機建議** |
| 6 | **我的供應商** | `/restaurant/suppliers` | 合作中供應商、準時率/短少率、評價入口 | **供應商健康度雷達** |
| 7 | **菜色實驗室** | `/restaurant/lab` | 用現有食材 + 當季便宜品項推薦新菜,附成本與建議售價 | **新菜研發助手** |
| 8 | **分店與成員** | `/restaurant/team` | 多分店管理、成員角色指派、採購簽核流程 | — |
| 9 | **店家設定** | `/restaurant/settings` | 店名/地址/類型/座位數、收貨時段、LINE 綁定 | — |
| — | **我的賣場**(商城模組) | `/restaurant/shop/*` | 料理包上架、訂單、合規文件、銷售分析 → 見第 5 節 | ⭐ **料理包商品化建議**<br>⭐ **AI 文案與標示生成** |

### 為什麼這樣排

- **第 2、5 頁是留存核心**。菜單成本毛利分析是全台灣只有 iFoodmap 算得出來的東西(因為我們同時有菜色組成 + 供應商真實報價),這是餐廳願意每個月付費的唯一理由。
- **第 3、4 頁是日活核心**。LINE 叫貨 + 拍照收貨,把使用門檻壓到「拍一張照」,老闆在廚房也能用。
- **第 4 頁同時修好收貨斷鏈**,GMV 從此可信。

## 4. 交易全生命週期追蹤(架構骨幹)

> 需求:**餐廳叫貨 → 供應商發貨 → 餐廳確認收貨 → 評價,每一個環節都要能在管理員後台查到。**

作法不是在 admin 多寫幾個查詢頁,而是**把訂單狀態機定死,每一次狀態變更都寫一筆不可竄改的事件**。
三端只是同一條事件流的不同視角,admin 天然就看得到全部。

### 4.1 訂單狀態機

```
  [餐廳端]                [平台]              [供應商端]           [餐廳端]
                                                                        
  draft ──► submitted ──► dispatched ──► accepted ──► quoted ──► confirmed
  建立需求    送出/簽核      派發供應商      供應商接單    報價      餐廳確認
                                                                        │
                                                                        ▼
  closed ◄── reviewed ◄── received ◄── delivered ◄── in_transit ◄── shipped
  結案對帳      評價        ★餐廳收貨      標記送達       運送中      供應商出貨
```

**異常分支**(全部都要能在 admin 查到):

| 分支 | 觸發者 | 說明 |
|---|---|---|
| `rejected` | 供應商 | 拒單 → 平台需重新派發 |
| `discrepancy` | 餐廳 | 收貨有差異(短少/規格不符/品質)→ 進爭議流程 |
| `disputed` | 任一方 | 正式爭議,admin 介入 |
| `cancelled` | 餐廳 / admin | 取消,需記錄原因 |
| `expired` | 系統 | 超時未回應(如供應商 24h 未接單) |

**關鍵原則:`received` 只能由餐廳端觸發**(或 admin 代為補登並記錄是代登)。
供應商說「我送到了」只能推到 `delivered`。這一條規則就是 GMV 可信度的來源。

### 4.2 事件流:`order_events`

每一次狀態變更、每一個動作,都 append 一筆:

```sql
order_events (
  id, order_id,
  from_status, to_status,
  actor_id,        -- 誰做的(user id;系統事件為 null)
  actor_role,      -- restaurant / supplier / admin / system
  source,          -- restaurant_portal / supplier_portal / admin_portal / line_bot / api / cron
  payload jsonb,   -- 該動作的細節(報價金額、出貨明細、收貨差異、評價內容…)
  note text,
  created_at
)
```

- **只 append,不 update、不 delete** → 稽核軌跡完整,爭議時有據可查
- 訂單主表的 `status` 只是「最新事件的快照」,真相在事件流
- `source` 欄位讓你知道**這筆單是從哪個介面來的**(例如 LINE 叫貨佔比多少)

這張表同時餵養:訂單履歷頁、流程看板、卡關預警、履約評分(準時率/短少率)、成長儀表板的漏斗。

### 4.3 Admin 的三個視角

**① 交易全流程看板 `/admin/pipeline`**

所有進行中訂單依階段排成看板,每張卡顯示「已停留時間」:

```
待接單(3)   待報價(5)   待出貨(8)   運送中(12)   待收貨(6)   待評價(9)
  ⚠ 18h       ⚠ 2d                                 ⚠ 3d
```

- 超過門檻自動變紅 → **admin 一眼看出卡在哪、該催誰**
- 這是你的日常營運中控台,也是 demo 給投資人時最有說服力的一頁

**② 訂單履歷 `/admin/orders/:id`**

單筆訂單的完整時間軸,每一格都是一筆 `order_events`:

```

07/20 16:02  餐廳確認訂單                        (line_bot)
07/21 06:15  供應商出貨(黑貓 1234-5678)         (supplier_portal)

```

- 附:雙方聯絡資訊、原始 AI 分析、報價明細、送貨單照片、評價全文
- **爭議時這一頁就是唯一事實來源**

**③ 卡關預警**

`order_events` 的最新事件超過門檻沒有下一步 → 進 admin 首頁的待辦區:

| 卡點 | 門檻 | 動作 |
|---|---|---|
| 派發後未接單 | 24h | 催供應商 / 改派 |
| 接單後未報價 | 24h | 催報價 |
| 報價後餐廳未確認 | 48h | 提醒餐廳 |
| 出貨後未標記送達 | 48h | 催供應商 |
| **送達後餐廳未確認收貨** | **72h** | **催餐廳(直接影響 GMV 認列)** |
| 收貨後未評價 | 7d | 提醒評價 |

### 4.4 三端如何寫入同一條事件流

| 環節 | 誰做 | 從哪個頁面 | 寫入 |
|---|---|---|---|
| 叫貨 | 餐廳 | `/restaurant/purchase` 或 LINE | `draft → submitted` |
| 簽核 | 店長 | `/restaurant/purchase` | `submitted`(附簽核人) |
| 派發 | 系統/admin | 媒合引擎 / `/admin/matching` | `→ dispatched` |
| 接單 | 供應商 | `/supplier/orders` | `→ accepted` |
| 報價 | 供應商 | `/supplier/quotes` | `→ quoted`(payload 含明細) |
| 確認 | 餐廳 | `/restaurant/orders` | `→ confirmed` |
| 出貨 | 供應商 | `/supplier/shipments` | `→ shipped`(payload 含物流單號) |
| 送達 | 供應商 | `/supplier/logistics` | `→ delivered` |
| **收貨** | **餐廳** | **`/restaurant/orders`** | **`→ received`**(payload 含送貨單照片與差異) |
| 評價 | 餐廳 | 收貨後自動彈出 | `→ reviewed`(payload 含評分與評語) |
| 結案 | 系統 | 對帳完成 | `→ closed` |

**現況要修的兩個地方:**
1. 物流頁靠 `notes.includes('送達')` 字串比對判斷送達([SupplierLogisticsPage.tsx:25](../src/pages/supplier/SupplierLogisticsPage.tsx))→ 改讀正式狀態
2. `supplier_reviews` 沒驗證買過,任何登入帳號都能評 → 改成 `order_reviews`,RLS 要求該筆訂單已 `received` 且屬於該餐廳

## 5. 料理包商城(餐廳從買方變賣方)

> 需求:**iFoodmap 不只是雙邊 AI 系統商,還是集中入口 —— 餐廳可以在 iFoodmap 商城上架自己研發的真空料理包。**

### 5.1 為什麼這一步很強

餐廳研發出好料理包,最大的困難不是做,是**沒有通路**:自己開蝦皮沒流量、進超商門檻極高、擺店裡只賣得到熟客。

iFoodmap 有一件事**蝦皮、momo、Pinkoi 永遠做不到**:

> 我們已經有這家餐廳的**菜單、菜色組成、食材成本**。
> 所以我們能主動告訴他:「你的紅燒牛腩最適合做料理包 —— 耐冷凍、成本穩定、
> 單份成本 NT$62,同類商品行情 NT$180-220,建議售價 NT$199,毛利率 69%。」

**而且它形成反向閉環:**

```
   餐廳採購食材 ──► 做出料理包 ──► 在商城賣 ──► 賣得好
        ▲                                          │
        └──────── 需要採購更多食材 ◄───────────────┘
```

料理包賣得越好,本業採購 GMV 也跟著漲。**平台從單邊抽成變雙邊抽成,而且兩邊互相放大。**
對投資人來說,這也把故事從純 B2B 延伸出 B2C 的想像空間。

### 5.2 ⚠️ 法規門檻(必須先處理,否則平台連帶責任)

**真空料理包在法規上是「食品製造」,不是「餐飲業」。**多數餐廳沒有以下資格:

| 項目 | 要求 | 平台如何把關 |
|---|---|---|
| **食品業者登錄** | 非登不可(食藥署),餐飲業與食品製造是不同類別 | 上架前必填登錄字號,系統可驗證格式 |
| **場所資格** | 自製包裝食品需符合 GHP;規模達標需工廠登記 | 上架申請時勾選並上傳證明 |
| **完整食品標示** | 品名、內容物、淨重、廠商、有效日期、保存方式、**過敏原**、營養標示 | ⭐ AI 生成標示草稿 + 人工審核 |
| **殺菌驗證** | 真空包裝低酸性食品有**肉毒桿菌風險**;需高溫殺菌(F值)或全程冷凍/冷藏 | 上架時必選保存方式,冷鏈品項標記 |
| **廣告用語** | 《食安法》第 28 條禁止療效、誇大宣稱 | ⭐ AI 自動掃描文案違規用語 |
| **產品責任險** | 出事時的財務防線 | 上傳保單,到期自動提醒 |

**設計原則:合規把關做成平台功能,而不是免責條款。**
`/admin/shop/compliance` 管所有文件與效期,**到期自動下架**。
這一層看似麻煩,實際上是:① 平台的法律防火牆 ② 對餐廳的真實價值(幫他們搞定最頭痛的事)
③ **競爭門檻**——蝦皮不會幫賣家做這件事。

### 5.3 分三階段上線(不要一次做成 B2C)

一次做到 B2C 要同時開金流、冷鏈、客服、行銷四條戰線,會拖垮種子輪節奏。建議:

| 階段 | 模式 | 買家 | 需要的新基礎設施 |
|---|---|---|---|
| **S1 展示 + 詢單** | B2B | 其他餐廳、團膳、企業福委、通路商、伴手禮採購 | **幾乎不用**——重用現有詢價/報價/訂單流程 |
| **S2 線上直接下單** | B2B | 同上 | 接現有金流 + 出貨流程 |
| **S3 開放 B2C 商城** | B2C | 一般消費者 | 冷鏈物流、消費者客服、退換貨、流量行銷 |

**S1 幾乎是免費的**:料理包就是一種「商品」,買家送詢價、賣家報價、出貨、收貨、評價 —— 完全共用第 4 節的訂單狀態機與事件流。**先用 S1 驗證有沒有人要買,再決定要不要投 S3 的重資產。**

### 5.4 餐廳端:我的賣場 `/restaurant/shop/*`

| 頁面 | 路由 | 內容 | AI 功能 |
|---|---|---|---|
| **賣場總覽** | `/restaurant/shop` | 本月銷售額、熱銷品、待出貨、庫存預警、合規到期提醒 | — |
| **商品管理** | `/restaurant/shop/products` | 料理包上架:照片、品名、規格、內容物、保存方式與效期、售價、庫存 | ⭐ **AI 商品文案 + 標示生成**<br>⭐ **違規用語檢查** |
| **商品化建議** | `/restaurant/shop/ideas` | 從你的菜單挑出最適合做料理包的菜色,附成本試算與建議售價 | ⭐⭐ **料理包商品化建議**(平台獨有) |
| **銷售訂單** | `/restaurant/shop/orders` | 收到的訂單/詢價、出貨、對帳 | — |
| **合規文件** | `/restaurant/shop/compliance` | 食品業者登錄、檢驗報告、保單上傳與效期管理 | **缺件檢查清單** |
| **銷售分析** | `/restaurant/shop/analytics` | 誰在買、回購率、哪個通路來的、毛利 | — |

**兩個 AI 功能的細節:**

**① 料理包商品化建議**(最有價值,也最不可複製)
輸入:餐廳現有菜單 + 菜色食材組成 + 平台即時食材價格
輸出:每道菜的「料理包適合度」評分,考量——
- 耐冷凍/復熱後風味變化(依食材類型,建圖譜)
- 食材成本穩定度(價格波動大的不適合固定售價)
- 製程複雜度、保存難度
- 同類商品市場行情與競爭密度
→ 直接給「建議售價、預估毛利、預估月銷量」

**② AI 文案與標示生成**
輸入:商品照片 + 食材清單 + 重量
輸出:商品描述、成分表(依含量排序)、**過敏原標示**、營養標示草稿、保存與復熱說明
→ 同時掃描是否有療效宣稱等違規用語,標紅提示
**這解決了餐廳做料理包最卡的環節之一**(標示做錯會被開罰)

### 5.5 商城前台(公開)

| 頁面 | 路由 | 說明 |
|---|---|---|
| **商城首頁** | `/shop` | 依料理類型、地區、價格帶瀏覽;主打「餐廳直出、名店私房菜」 |
| **商品頁** | `/shop/p/:id` | 商品詳情、標示資訊、保存方式、餐廳介紹、評價 |
| **餐廳品牌館** | `/shop/s/:restaurantId` | 該餐廳的所有料理包 + 餐廳故事 → **對餐廳是免費行銷,對平台是留存** |
| **詢價/下單** | — | S1 走詢價;S2 之後接金流 |

### 5.6 訂單如何併入現有架構

料理包訂單**共用第 4 節的狀態機與 `order_events`**,只差在角色對調:

| | 食材採購單 | 料理包訂單 |
|---|---|---|
| 賣方 | 供應商 | **餐廳(賣場)** |
| 買方 | 餐廳 | 其他餐廳/通路商/消費者 |
| 狀態機 | 同一套 | **同一套** |
| 事件流 | `order_events` | **同一張表**,以 `order_type` 區分 |

好處:admin 的訂單履歷、全流程看板、卡關預警、履約評分**全部自動涵蓋料理包**,不用重做一遍。

## 7. 建議施作順序

依「對種子輪的幫助」× 「實作成本」排序:

### 階段一 — 修補閉環 + 全流程追蹤(最優先,決定數字可不可信)
1. **訂單狀態機 + `order_events` 事件流**(第 4 節)—— 這是骨幹,後面全部依賴它
2. `restaurants` / `restaurant_accounts` + `role='restaurant'` + `/restaurant` 骨架
3. **餐廳端訂單與收貨頁**(含「已收到貨」按鈕)→ GMV / 複購率變成可信數字
4. **admin 訂單履歷 `/admin/orders/:id` + 全流程看板 `/admin/pipeline`** → 全環節可查
5. **送貨單拍照對帳** → demo 效果最強,同時防弊
6. **交易評價(`order_reviews`)+ NPS** → 盡調第三題有答案
7. `/admin/restaurants` + `/admin/suppliers` 會員管理
8. 卡關預警(接在 `order_events` 上,幾乎免費)

### 階段二 — 留存與 GMV(三個月內做完)
9. **供應商商機雷達** → 直接推 GMV
10. **菜單成本毛利分析** → 餐廳端付費錨點
11. **AI 報價草稿** + **拍照自動上架** → 降低雙邊摩擦
12. `/admin/growth` 成長儀表板 → 投資人簡報直接截這一頁

### 階段三 — 護城河(邊做邊補,pitch 要講)
13. **食材主檔 + 規格標準化引擎**(`/admin/ingredients`)
14. **菜色↔食材對應校正**(`/admin/dishes`)→ 資料飛輪
15. **媒合品質監控** → 演算法從規則式升級成學習式
16. LINE 叫貨、替代建議、動態定價、需求預測升級

### 階段三.5 — 料理包商城 S1(可與階段二並行,成本極低)
17. `seller_profiles` / `seller_compliance` + `/admin/shop/compliance` 合規把關(**先做,這是前提**)
18. `shop_products` + `/restaurant/shop/products` 上架 + `/admin/shop/products` 審核
19. `/shop` 公開商城 + 商品頁 + 餐廳品牌館(S1 走詢價,共用現有訂單流程)
20. ⭐ **料理包商品化建議** `/restaurant/shop/ideas` ← 平台獨有,demo 亮點
21. ⭐ **AI 文案與標示生成 + 違規用語檢查**

### 階段四 — 規模化
22. 商城 S2(線上直接下單)→ S3(開放 B2C,需冷鏈與客服)
23. 同區集單團購、雙邊履約信用評分、帳期金融、爭議處理

## 8. 對投資人的敘事

三端架構本身就是一個好故事:

> **我們不是在做一個媒合網站,是在做食材產業的作業系統。**
> 餐廳用我們管成本、供應商用我們找生意、每一筆交易都在餵養
> 「菜色 ↔ 食材 ↔ 規格 ↔ 價格」的知識圖譜。
> 用得越多越準,越準越沒人追得上。

競品(美菜、Choco、REKKI)手上只有**訂單紀錄**;iFoodmap 有**餐廳在賣什麼**。
這讓需求預測從「看歷史推未來」升級成因果推論:
「這季台中北區新開 12 家火鍋店、菜單都有毛肚 → 未來三個月毛肚需求 +35%,
但服務該區有貨的供應商只有 2 家」——**這是招商和定價的武器,也是護城河**。
