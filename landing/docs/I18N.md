# 中英雙語怎麼運作

> 2026-09-22 上線。中文是預設語系,英文是 `/en` 前綴。
> 2026-09-24 改:裸網址 `/` 不再依瀏覽器語系自動轉,改成提示條(理由見下)。

## 一句話版本

**網址決定渲染哪個語系;只有「按過語言鈕」的紀錄(localStorage)能讓裸網址 `/` 自動轉。
瀏覽器語系只拿來「建議」(首頁頂端的提示條),絕不拿來轉址。**

| 網址 | 語系 |
|---|---|
| `/`、`/restaurants`、`/suppliers`、`/cases`、`/about`、`/contact` | 中文 |
| `/en`、`/en/restaurants`、`/en/suppliers`、`/en/cases`、`/en/about`、`/en/contact` | English |

## 自動切換的規則(2026-09-24 起:只有「按過語言鈕」才轉)

使用者連到**裸網址 `/`** 時:

| 情境 | 行為 |
|---|---|
| 按過語言鈕(`localStorage['ifm.lang']` 有值)、而且跟頁面不同 | **自動轉**到他選的版本,`history.replaceState`、**不留歷史紀錄**(按上一頁不會被彈回來) |
| 沒按過,只是瀏覽器語系(`navigator.languages`)跟頁面不同 | **不轉**。頁面頂端出現一條語系提示條(見下一節) |
| 瀏覽器語系跟頁面相同,或認不得(例如只設了日文) | 什麼都不做 |

深層網址(`/restaurants`、`/en/about`…)一律照網址渲染,**就算按過語言鈕也不轉**。

邏輯在 `routing.js` 的 `applyPreferredLang()`(呼叫端只准傳 `IfmI18n.storedLang()`)
與 `i18n.js` 的 `suggestLang()`;測試釘在 `tests/routing.test.cjs` 與 `tests/i18n.test.cjs`,
真瀏覽器的回歸檢查是 `npm run smoke`(用「偏好英文、什麼都沒存過」的瀏覽器跑 22 條網址)。

### 為什麼不再依瀏覽器語系自動轉

2026-09-24 在正式站實測:用 Googlebot 的語系設定(`navigator.languages = ['en-US']`、
localStorage 空的)打開 `/`,跑完 JS 後網址列變 `/en`、canonical 變 `/en`、`<html lang>` 變 `en`、
h1 變英文 —— 但 hreflang 仍然說中文版是 `/`。「`/` 的內容是英文、canonical 指向 `/en`」跟
hreflang 互相矛盾,Google 會忽略指向非標準網址的 hreflang,中英互指斷掉,中文首頁可能被併進英文版。
Google 官方也明講不要依「推測的使用者語系」自動轉址。業主裁決:**按過語言鈕才自動轉,其餘改成提示條**。

按過語言鈕是使用者明確的選擇,Googlebot 永遠不會有(它每次都沒有 localStorage),所以這條轉址安全。

### 為什麼深層網址不自動轉

`/suppliers` 直接進來就是中文,不管瀏覽器設什麼、也不管按過什麼。**這是刻意的**:
深層網址多半是從搜尋結果或分享連結進來的,網址本身就是「要看哪個語系」的答案;
而 Googlebot 以 en-US 渲染每一頁,如果深層網址也自動轉,中文版就會被整批踢到英文版、永遠索引不到。

想看英文版的深層頁就走 `/en/suppliers` —— 那是真實網址,分享得出去、爬得到。

## 語系提示條

瀏覽器語系跟頁面不同、又還沒表態過的訪客,首頁頂端會出現一條細橫條,例如中文首頁上給英文訪客看的
「Prefer English? Switch to English →」。規則全部在 `i18n.js` 的 `suggestLang(win, page, lang)`,全部成立才出現:

1. 在**首頁**(`/` 或 `/en`)。深層頁不出現 —— 那多半是從搜尋結果或分享連結進來的,人已經在看他要的東西;
   而且 Googlebot 以 en-US 渲染,只放首頁的話它在中文頁上看到的英文句子就只有 `/` 這一處
2. 沒按過語言鈕(`ifm.lang` 沒有值)
3. 沒按過提示條的 ×(`localStorage['ifm.langHintDismissed'] = '1'`)
4. 瀏覽器語系認得出來(zh / en),而且跟頁面不同

| 動作 | 效果 |
|---|---|
| **切換** | 跟按 header 的語言鈕完全同一件事:寫 `ifm.lang`、換網址(pushState)、發 `ifm:langchange`。之後再來 `/` 就會自動轉 |
| **×** | 收起來,寫 `ifm.langHintDismissed`。**刻意跟 `ifm.lang` 分開** —— 關掉提示條不代表選了中文,也不代表選了英文,`/` 的落地不受影響 |

兩個動作之後焦點都交給 header 的 logo(原本再按一次 Tab 會到的地方),不會掉回 `<body>`。
無痕視窗寫不進 localStorage:元件另外在記憶體記一個 `langHintOff`,至少這一頁收得掉。

**文案用「建議的那個語系」寫**:中文頁上的提示條是英文、英文頁上的是中文 —— 讀它的人正是看不懂這一頁的人。
所以字典裡 `zh.langHint` 是中文、`en.langHint` 是英文,元件取的是 `dict(建議語系).langHint`,**不是 `L`**;
整條提示條標 `lang="en"` / `lang="zh-Hant"`,螢幕閱讀器才會用對的發音。

其他細節:

- 位置在 skip link 之後、header 之前,**main 地標外面**(它不是頁面內容);跟著文件流、不 fixed,捲下去就走
- `role="region"` + `aria-label`;字 16px、兩個點擊區 44px(手機也一樣);`data-nosnippet`(不讓這句話變成搜尋摘要)
- **不會被烤進預渲染的靜態 HTML**:預渲染時瀏覽器語系鎖成跟路由同一個語系、storage 清空,提示條本來就不會出現;
  `scripts/prerender.mjs` 的 `RUNTIME_ONLY_NODES` 再把 `.ifm-langhint` 剝一次當保險。不跑 JS 的爬蟲看不到它

## 檔案分工

| 檔案 | 負責 |
|---|---|
| `i18n.js` | 整份中英字典 + 語系偵測/記憶 + 提示條規則(`suggestLang` / `dismissHint`)。UMD,node 可 `require`,所以測試跑得到 |
| `routing.js` | 網址 ↔ `{page, lang}`、canonical、hreflang、`<html lang>`、og:locale |
| `index.html` | markup 用 `{{ L.xxx.yyy }}` 綁定;`renderVals()` 把 `L` 餵給模板 |
| `vercel.json` | 12 條 rewrite(中文 5 + `/en` + 英文 5),全部指向 `/` |

### 改文案

直接改 `i18n.js` 裡 `DICT` 的值就好,markup 不用動。
**zh 與 en 的 key 結構必須完全一致** —— 少一個 key 的症狀是畫面上那行字**直接消失**
(support.js 只 `console.warn`,不會報錯),`tests/i18n.test.cjs` 有擋這件事。

### 新增一頁

1. `routing.js` 的 `pageByPath` / `pathByPage` 各加一筆
2. `vercel.json` 加兩條 rewrite(`/新頁` 與 `/en/新頁`)
3. `i18n.js` 的 `meta.pages` 補該頁的 title / description(兩個語系)
4. markup 加一個 `<sc-if value="{{ is新頁 }}">` 區塊

## 三個踩過的坑

### 1. 相對路徑在 `/en/` 之下會整個歪掉

`<script src="./support.js">` 在 `/en/suppliers` 之下 base 變成 `/en/`,
會去要 `/en/support.js` → 404 → **整個框架不載入、頁面全白**。
圖片 `assets/xxx.svg` 同理變成 `/en/assets/xxx.svg`。

中文版沒事只是因為 `/suppliers` 的 base 剛好還是 `/`,**是運氣不是設計**。
現在所有資源一律 root-absolute(`/support.js`、`/assets/…`),測試有釘。

### 2. 內部連結的 `href` 也要帶語系前綴

`onClick` 走 routing 換頁是對的,但 `href` 是**右鍵在新分頁開啟**、cmd+click、
以及爬蟲實際會走的路徑。英文頁上寫死 `href="/contact"` 會把人帶回中文站。
現在 markup 裡的內部連結一律是 `{{ hrefContact }}` 這類綁定。

### 3. `<title>` 不能放在 `<helmet>` 裡

support.js 的 helmet 把 `<link>` / `<meta>` **掛一次就不管**(所以用 JS 改它們是安全的),
但 `<title>` 進的是 live map,**每次 render 都會被重設回原始碼那行字**。
所以 `<title>` 搬到真正的靜態 `<head>`,由 `Component.syncSeo()` 依語系與頁面覆寫。
順帶好處:不跑 JS 的社群爬蟲現在讀得到標題(以前整頁沒有 `<title>`)。

## 所有「送出媒合」都走 AI 助手

2026-09-23 起,`/contact` 上那張需求單表單**已經移除**,連帶它的 Supabase 漸進增強 script
也刪了(那段本來就只為表單存在)。現在這幾個按鈕一律打開右下角的 AI 採購助手:

| 位置 | 文案 |
|---|---|
| header(桌機 + 手機抽屜) | 填寫食材需求 / Post a Request |
| 首頁流程區結尾 | 立即填寫食材需求 / Post Your Request |
| 首頁結尾 CTA | 填寫食材需求 / Post a Request |
| `/contact` 的大按鈕 | 開始對話,免費媒合 → / Start chatting — free → |

這些都是 `<a href="/contact">` 或 `<button>` 掛 `onClick="{{ openAI }}"`。
**`href` 刻意留著** —— 助手還沒載好或使用者關掉 JS 時,`openAI()` 不會 `preventDefault`,
瀏覽器就照 href 走到聯絡頁,不會按了沒反應。

不改的:`聯絡我們`、`常見問題`、`建立餐廳帳號`、`申請供應商上架` —— 那些不是媒合請求。

lead 沒有少收:助手問完四題後本來就會收姓名與手機,自己寫進 `landing_leads`
(`source` 欄位分得出來是哪一條路徑進來的)。

## AI 採購助手

右下角的 widget 在 React 之外,沒有 state 可以重繪,所以靠事件換字:
切語系時 `Component.switchLang()` 會發 `window` 的 `ifm:langchange`,
widget 訂閱它重寫自己的靜態文字。**已經送出的對話訊息不會被回頭翻譯**(那是歷史紀錄)。

打去 `/api/ai-chat`、`/api/ai-menu`、`/api/ai-extract` 的 body 都會帶 `lang`,
主專案的 Supabase Edge Function `ai` 看到 `lang: "en"` 會讓回覆、菜單分析的品名與摘要
全部改用英文(見 `ifoodmap/supabase/functions/ai/index.ts` 的 `withLang()`)。

寫進 `landing_leads` 的 `detail` 欄位**維持中文標籤** —— 那是給台灣業務看的內部欄位,
翻了反而看不懂。
