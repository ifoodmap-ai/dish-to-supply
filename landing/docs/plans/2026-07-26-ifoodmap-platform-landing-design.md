# iFoodmap 雙邊平台 Landing 與餐廳自助註冊設計

日期：2026-07-26

## 目標

將 iFoodmap Landing 從以「AI 食材媒合」為主的單一形象網站，升級為同時服務餐廳與供應商的雙邊 B2B 食材採購平台入口。

這次保留既有品牌視覺與動效，重整文案、內容結構與公開頁面路由，並在主產品補上餐廳自助註冊及立即開通流程。

## 已確認的產品決策

- Landing 同時面向餐廳與供應商，不偏重其中一方。
- 首屏使用「我是餐廳／我是供應商」雙入口並列。
- 調整範圍包含文案、區塊增刪、區塊重排與產品功能示意畫面，不全面重做視覺。
- 採用「平台首頁＋餐廳方案頁＋供應商方案頁」架構。
- 功能畫面依現有主產品介面製作行銷用 mockup，不使用真實商業資料。
- Landing 與主產品一起改，餐廳可直接註冊並立即進入後台。
- 現有營運數字、客戶心得與案例成果先保留，視為已核准的行銷內容。

## Landing 技術設計

保留現有 `index.html + support.js` 架構與品牌動效，不重寫成 React 或 Next.js。

### 公開路由

使用 History API 將現有前端狀態切換升級成可分享的網址：

- `/`
- `/restaurants`
- `/suppliers`
- `/cases`
- `/about`
- `/contact`

需求：

- 首次載入時依 `window.location.pathname` 選擇頁面。
- 站內切換時呼叫 `history.pushState`。
- 監聽 `popstate` 支援瀏覽器上一頁與下一頁。
- Vercel 設定 fallback rewrite，讓子路徑直接載入及重新整理時仍回傳 `index.html`。
- 導覽與 CTA 使用具語意、可鍵盤操作的連結或按鈕。

### 相容性

- 保留現有 Landing 需求表單。
- 保留現有 AI 對話、菜單上傳及 AI 擷取 API。
- 不修改 `support.js`。
- 保留既有響應式與 reduced-motion 行為。

## 餐廳自助註冊

主產品新增 `/register/restaurant`。

### 表單欄位

- 餐廳名稱
- 聯絡人姓名
- 聯絡電話
- Email
- 密碼
- 確認密碼
- 同意服務條款

### 建立流程

1. 建立 Supabase Auth 使用者。
2. 以安全、限 authenticated 使用者呼叫的資料庫 RPC 建立餐廳。
3. 在同一筆資料庫交易中：
   - 建立 `restaurants`
   - 建立預設「總店」`restaurant_branches`
   - 建立註冊者的 `restaurant_accounts`
   - 將角色設為 `owner`
4. 完成後直接導向 `/restaurant`。
5. 餐廳後台顯示簡短的新手引導。

若正式 Supabase Auth 目前要求 Email 驗證後才建立 session，需調整成帳號立即可使用、登入後提醒驗證，才能符合立即開通決策。

### 安全與錯誤處理

- RPC 以 `auth.uid()` 為唯一帳號來源，不接受前端傳入任意 `user_id`。
- RPC 驗證必要欄位、限制合理長度，並防止重複建立。
- 餐廳、分店與 owner 關聯必須在同一筆交易成功或全部回滾。
- Email 已存在時引導登入，不重複建立帳號。
- 弱密碼、欄位錯誤、網路失敗及重複送出均顯示明確中文訊息。
- 送出中停用按鈕。
- 失敗後保留非密碼欄位，密碼依安全原則清除。
- 新帳號只能讀寫自己所屬餐廳資料；沿用現有 RLS 與 `current_restaurant_ids()`。
